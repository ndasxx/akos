# Домашнее задание №4

Сиротина Дарья Николаевна, БПИ253. Вариант 23 «Огонь по движущимся танкам».

## 1. Постановка задачи

На прямоугольном поле перемещаются танки, а одно или несколько орудий пытаются их поразить. Каждый танк занимает одну клетку и на каждом такте может остаться на месте либо перейти в соседнюю допустимую клетку. Орудие получает сведения о последнем известном положении цели и выбирает координаты выстрела по случайной или прогнозирующей стратегии (не обязательно в позицию танка, пытаясь предугадать его возможное перемещение). Выстрел имеет задержку между наведением и попаданием. После формирования выстрела танк может переместиться, поэтому снаряд поражает указанную клетку, а не идентификатор цели. В одной клетке действуют правила прямого попадания, близкого разрыва и промаха.

Требуется разработать консольное приложение, моделирующее огонь по движущимся целям. В данном задании каждый танк, каждое орудие, а также координатор поля являются **сетевыми программами**, взаимодействующими через TCP-сокеты: система должна работать и на одной машине, и в распределённом варианте, когда программы запущены на разных компьютерах. Асинхронность взаимодействия обеспечивается изученными сетевыми средствами (мультиплексирование ввода-вывода `poll`, неблокирующее ожидание готовности через `select`) в сочетании с многопроцессностью: каждая программа - самостоятельный процесс. Сценарий завершения описан ниже (раздел 5).

**Входные параметры** - те же, что в прошлых заданиях: размеры поля и препятствия, число и начальные позиции танков и орудий, стратегии движения, дальность наблюдения, задержка и точность выстрела, радиус поражения, запас снарядов и прочность танков, предельное число тактов. Дополнительно у каждой программы - сетевые параметры `--host` и `--port`.

**Отображаемые события** - те же семь: перемещение танка, наблюдение цели, выбор точки прицеливания, выстрел, фактическое положение цели в момент попадания, промах, повреждение и уничтожение. Каждая программа выводит только ту информацию, которая проходит через её соединение: танк видит свои решения, орудие - свои, монитор - полный снимок такта.

**Инварианты** модели сохранены без изменений: танк не выходит за границы и не проходит через препятствие; один выстрел расходует один снаряд; попадание определяется по состоянию поля в момент разрыва; уничтоженный танк больше не перемещается и становится препятствием; прочность не уходит в минус без фиксации уничтожения. К правилам добавлен сетевой инвариант: сервер - единственный владелец состояния, любое решение клиента проходит валидацию на сервере перед применением.

**Завершение.** Моделирование завершается после уничтожения всех танков, исчерпания боеприпасов или достижения ограничения тактов, или по прерыванию пользователем (`SIGINT` на сервере либо команда `stop` оператора). При любом из этих способов сервер рассылает всем подключённым клиентам сообщение об останове с причиной, и каждая программа завершается сама с кодом 0.

## 2. Сценарий

Отображение сущностей модели на сетевые программы и файлы кода:

| Сущность модели | Сетевая программа | Общие файлы |
|---|---|---|
| Поле (координатор) | `server` - слушающий сокет, авторитетное состояние, цикл тактов | `server.c`, `field.c`, `logic.c` |
| Танк i | `tank_client --id i` | `tank_client.c`, `logic.c` |
| Орудие j | `gun_client --id j` | `gun_client.c`, `logic.c` |
| Монитор (интегральный вывод) | `monitor` - пассивный подписчик снимков; допускается несколько одновременно, подключение и отключение в любой момент | `monitor.c` |
| Оператор | `control` - текстовая консоль: список клиентов, отключение клиента, останов сервера | `control.c` |
| Состояние поля, танков, орудий, снарядов | структура `SharedState` внутри `server`; клиентам передаются снимки сообщением `Msg` | `state.h`, `proto.h`, `net.c` |
| Генератор случайных чисел | `struct Rng` на `rand_r`; сервер и клиенты инициализируют свои ГСЧ детерминированно из общего seed (`seed`, разведённого по номеру сущности), поэтому на одном seed распределённая система воспроизводит результаты однопроцессной | `rng.c` |

Модельное время - целочисленное (`long long tick`). Внутри такта четыре фазы в фиксированном порядке: `MOVE` (перемещения танков), `OBSERVE` (наблюдения орудий), `FIRE` (выстрелы), `IMPACT` (разрывы снарядов). Порядок обеспечивает инвариант «попадание определяется по состоянию поля в момент разрыва».

Правила модели (поле, стратегии движения, наблюдение, выстрел, урон, статистика) полностью унаследованы из заданий 2-3 и здесь не дублируются; перенесены без изменений вместе с тестами на повторяемость.

## 3. Пользовательский интерфейс

Каждая программа печатает только свою часть картины - всё, что она знает, получено по сети от сервера.

### 3.1. Сервер

Баннер с параметрами и адресом, строку подключения каждого клиента (`подключён танк #1 (pid ...) - 1/3`), заголовки тактов, авторитетные события модели (выстрелы, попадания, повреждения, уничтожения - их печатает функция применения решения, поэтому событие появляется ровно один раз и ровно там, где реально изменилось состояние), итоговую статистику (таблицы орудий и танков, сводка выстрелов/попаданий) и причину завершения.

### 3.2. Клиент-танк

Сообщения о подключении и текущем такте, собственные решения: `решение: шаг (x,y) -> (x',y')` или `решение: остаюсь на (x,y)`. Ничего о чужих танках и орудиях танк не знает и не печатает.

### 3.3. Клиент-орудие

Наблюдения (`наблюдение: цель #k в (x,y)` или `целей в радиусе нет`), прицеливание (`прицел -> (x,y)`), состояние перезарядки (`перезарядка (такт N < M)`), подтверждения выстрелов сервером.

### 3.4. Монитор

Комплексный снимок каждого такта, приходящий с сервера: поле целиком (танки - `T`, орудия - `G`, обломки - `#`), затем таблицы «Танки» (состояние жив/УНИЧТОЖЕН, прочность, позиция, число шагов, попадания по нему), «Орудия» (патроны, выстрелы, попадания, текущая цель), число снарядов в полёте и накопленная статистика. Это интегральный вывод, которого нет ни у одного участника по отдельности.

### 3.5. Оператор (`control`)

Приветствие с адресом сервера и строка `введите команду (help - справка, Ctrl+D - выход)`; команды `list`, `kick tank N`, `kick gun N`, `kick monitor`, `stop`, `help`, `quit`; ответы сервера печатаются по мере поступления. Ввод построчный, работа по конвейеру (`echo "list" | ./control ...`) допускается.

## 4. Варианты запуска

Программы независимы: у каждой свои `--host`/`--port`, поэтому конфигурация сети полностью гибкая — все на одной машине, сервер на одной, клиенты на других, несколько машин. Клиенты сами повторяют `connect` каждые 100 мс в течение 30 с, поэтому порядок и момент запуска не важен: можно запускать сущности раньше сервера, одновременно, добавлять мониторы и оператора в любой момент игры.

Один компьютер (порт по умолчанию 7777):

```bash
./server --seed 42 --delay 100 --max-ticks 200 --log tank_sim.log --port 7777 &
./tank_client --id 1 --port 7777 &
./tank_client --id 2 --port 7777 &
./tank_client --id 3 --port 7777 &
./gun_client  --id 1 --port 7777 &
./gun_client  --id 2 --port 7777 &
./monitor --port 7777 &        # можно несколько
./control --port 7777          # можно не запускать
```

Несколько компьютеров: на машине сервера `./server … --port 7777`, на остальных `./tank_client --id 1 --host АДРЕС_СЕРВЕРА --port 7777` и т.д. (`--host` по умолчанию `127.0.0.1`). Число и `--id` клиентов должны совпадать с `--tanks`/`--guns` сервера; неверный `id` отклоняется с пояснением, занятый слот - тоже.

Печать поля на каждом такте - опционально: `./server ... --verbose-field` (по умолчанию поле не печатается, печатаются только события). Полный список параметров - `./server --help` (модельные параметры те же, что в заданиях 2-3, плюс `--port`).

## 5. Завершение

Сценарий завершения единый для всех способов останова:

1. Сервер решает завершить работу: конец игры (все танки уничтожены / боезапас исчерпан / достигнут `--max-ticks`), `SIGINT` или команда `stop` оператора.
2. Сервер рассылает всем подключённым клиентам (танкам, орудиям, мониторам, операторам) сообщение `STOP` с кодом причины и текстом.
3. Каждый клиент печатает `сервер завершил работу (<причина>)` и завершается с кодом 0; монитор перед выходом печатает финальный снимок.

Отдельные случаи: убитый (`kill -9`) или зависший клиент не рушит игру - сервер замечает обрыв соединения за ~1 с (сторожевой таймаут на `poll`), печатает `клиент ... отключился - его фазы пропускаются` и продолжает такты; освободившийся слот может занять переподключившийся клиент с тем же `--id` (проверяется тестом). Мониторы подключаются и отключаются в любой момент, на остальных участников не влияя. Оператор может принудительно отключить любого клиента (`kick tank 2`) или всех мониторов (`kick monitor`) - отключённый клиент получает `KICK` с причиной. Аварийные остатки процессов после `kill -9` убирает `scripts/cleanup.sh`.

## 6. Протокол взаимодействия

Транспорт - TCP (дуплексный, потоковый). Первый байт соединения выбирает роль: `T` - танк, `G` - орудие, `M` - монитор, `C` - управление. Далее в потоке идут сообщения фиксированного размера - структура `Msg` (`include/proto.h`): номер фазы, идентификатор и pid сущности, номер такта, общий seed, снимок поля, массивы танков и орудий, снаряды, статистика, координаты хода/прицела, код причины и текстовое пояснение.

Фазы протокола:

| Фаза | Направление | Содержимое |
|---|---|---|
| `ATTACH` | клиент -> сервер | роль уже выбрана байтом, здесь `id` и pid |
| `WELCOME` | сервер -> клиент | seed (для разведения ГСЧ), текущий такт; после неё клиент работает по тактам |
| `MOVE` | сервер -> танк -> сервер | снимок поля; ответ - предлагаемый ход `(ax, ay)` |
| `OBSERVE` | сервер -> орудие -> сервер | снимок поля; ответ пустой (наблюдение обновляет локальную копию орудия) |
| `FIRE` | сервер -> орудие -> сервер | снимок поля; ответ - точка прицеливания; сервер сам решает, прошла ли перезарядка |
| `MON` | сервер -> монитор | полный снимок такта (без ожидания ответа) |
| `KICK` | сервер -> клиент | принудительное отключение с текстом причины |
| `STOP` | сервер -> всем | завершение с кодом причины и текстом |

Так как TCP - поток, поверх него реализованы `net_write_full`/`net_read_full` - циклы, дозаписывающие/дочитывающие сообщение при частичных `send`/`recv`. Запись с флагом `MSG_NOSIGNAL`, плюс `SIGPIPE` игнорируется процессом: обрыв соединения любым клиентом не должен убивать сервер. Ожидание ответа клиента `poll` с секундным таймаутом: такт не встаёт навсегда, если клиент завис, а не ответившая за 5 с сущность просто пропускает фазу. Маска ожидаемых событий включает `POLLIN | POLLERR | POLLHUP | POLLNVAL`, поэтому закрытое соединение и ошибки обнаруживаются сразу. Одновременно с фазами тот же цикл `poll` обслуживает слушающий сокет (новые клиенты), мониторы (запись снимков, обрывы) и консоли операторов (построчный приём команд с накоплением в буфер).

Сервер - единственный владелец состояния: клиент получает снимок и лишь предлагает решение, а сервер валидирует его против текущего состояния (границы, препятствия, занятость клетки, перезарядка, боезапас). Поэтому «взломанный» или ошибающийся клиент не может нарушить инварианты модели.

## 7. Реализация сервера (`server.c`)

Сервер - один процесс, один поток, мультиплексирование через `poll`. Состав:

- **Слоты подключений.** Массивы дескрипторов и pid для танков и орудий (слот свободен, пока -1), массивы мониторов (до 32) и операторов (до 8, у каждого - свой строковый буфер команд).
- **Старт.** Разбор параметров (`cfg.c` из заданий 2-3, неизвестные флаги игнорируются, поэтому сервер принимает и `--port`), поиск свободного порта при конфликте, `net_listen` (`SO_REUSEADDR`, очередь 16), построение начального состояния, ожидание подключения всех сущностей (`ATTACH`/`WELCOME`, отказ при неверном или занятом `id` с пояснением).
- **Цикл тактов.** Заголовок такта, опциональная печать поля (`--verbose-field`), задержка `--delay`, три фазовых обмена (`run_phase`), разрывы снарядов, проверка условий завершения, рассылка снимка мониторам, обслуживание новых подключений и команд оператора. Каждая фаза: снимок подключённым сущностям -> `poll` с таймаутом -> применение пришедших решений функциями `tank_apply_step`/`gun_observe_update`/`gun_apply_fire`, с торможением неответивших.
- **Команды оператора.** `list` - таблица подключённых с указанием слотов; `kick tank N` / `kick gun N` / `kick monitor` — принудительное отключение (освобождение слота); `stop` - корректный останов с рассылкой причины; `help`- справка. Ответы отправляются тому оператору, который команду послал.
- **Завершение.** При любой причине - `shutdown_all`: рассылка `STOP` с кодом причины и текстом всем живым соединениям, пауза 300 мс на доставку, закрытие всех дескрипторов, закрытие слушающего сокета. `SIGINT` обрабатывается через флаг (без `SA_RESTART`), поэтому останов замечается не позже секундного таймаута `poll`.

Сервер ведёт журнал `--log` (общий `log.c`).

## 8. Реализация клиентов (`tank_client.c`, `gun_client.c`)

Общая схема обеих программ: разбор `--id`/`--host`/`--port`, установка обработчиков сигналов (флаг, без `SA_RESTART`), `net_connect_retry` (каждые 100 мс до 30 с,  старт раньше сервера не ошибка), отправка байта роли и `ATTACH`, ожидание `WELCOME`. Отказ (`KICK` на этапе подключения - неверный или занятый `id`) печатается с пояснением сервера, программа завершается с ненулевым кодом. После `WELCOME` клиент инициализирует свой ГСЧ разведением общего seed по своему номеру.

Рабочий цикл: ждать готовности сокета (секундный таймаут - сторожевой таймер для ожидания фазы сервера и одновременно точка проверки флага сигнала), прочитать сообщение фазы, напечатать своё решение, отправить ответ. Для танка ответ - предлагаемый ход, для орудия - в фазе `OBSERVE` пустое подтверждение с обновлением локальной копии цели, в фазе `FIRE` - точка прицеливания по своей стратегии (с учётом перезарядки: клиент сообщает решение, а окончательно решает сервер - владелец состояния). `STOP` или обрыв соединения - печать `сервер завершил работу (<причина>)` (или `связь с сервером потеряна`) и выход с кодом 0.

## 9. Реализация монитора (`monitor.c`)

Программа подключается, отправляет байт роли `M` и дальше только читает: каждое сообщение `MON` - полный снимок такта, который печатается разделом «===== такт N =====» с полем и таблицами танков, орудий, снарядов и статистики. Монитор ничего не отправляет, его подключение и отключение (в том числе `kill -9`) никак не влияет на игру: сервер обнаруживает обрыв при следующей рассылке и убирает монитор из списка. Перед завершением по `STOP` монитор печатает финальный снимок.

## 10. Реализация оператора (`control.c`)

Текстовый клиент: подключение с ролью `C`, затем цикл побайтового чтения stdin и приёма ответов сервера. Накопление команд построчное, поэтому работа по конвейеру (`echo "list" | ./control --port 7777`) и интерактивный ввод ведут себя одинаково. После EOF stdin программа выдерживает секунду на последние ответы сервера и завершается. Команды: `list`, `kick tank N`, `kick gun N`, `kick monitor`, `stop`, `help`, `quit`.

## 11. Сводная таблица средств

| Задача | Средство |
|---|---|
| Транспорт | TCP-сокеты (`socket`, `bind`, `listen`, `accept`, `connect`), `SO_REUSEADDR` |

| Детерминизм | `rand_r` с разведением seed по номеру сущности (побайтовая повторяемость, проверено тестом) |
| Сериализация вывода | общий `io.c` (вывод через дескрипторы), журнал `log.c` |

## 12. Результаты

Демонстрационный прогон: поле 12×12, 8 препятствий, 3 танка со стратегией `random_walk`, 2 орудия (боезапас 25, дальность 7, перезарядка 2, задержка выстрела 2, точность 70%, прямой урон 3), seed 42. Игра завершилась уничтожением всех танков; сервер напечатал события (выстрелы, попадания, повреждения, уничтожения) и итоговые таблицы статистики, монитор - снимки каждого такта, каждый клиент - только свои решения.

Устойчивость к отказам проверена тестами: `kill -9` танка - сервер продолжает такты и печатает `клиент ... отключился - его фазы пропускаются`; `kill -9` монитора - незаметно для остальных; принудительный `kick` с переподключением того же танка под тем же `id` - слот освобождается и занимается заново; `stop` и `SIGINT` - все подключённые программы завершаются с кодом 0, печатая причину.

## 13. Тестовые наборы

`tests/run_all.sh` (запуск `make test`) выводит только статус каждой проверки и итоговую сводку; подробные логи в `tests/out/*.log`. 17 проверок:

| Тест | Что проверяет |
|---|---|
| `server_help`, `tank_help`, `gun_help`, `monitor_help`, `control_help` | справка `--help` каждой программы |
| `scenario` | полный сценарий: штатное завершение, статистика, события, корректный выход клиентов по `STOP` |
| `monitor` | монитор получает комплексные снимки (поле, танки, орудия, статистика, уничтожения) |
| `two_monitors` | два монитора одновременно получают снимки |
| `monitor_rejoin` | монитор убит (`kill -9`), новый подключился в ходу - сервер продолжает работу |
| `kick_reconnect` | оператор отключает танк #2, танк переподключается и доигрывает |
| `kill_tank` | `kill -9` танка: сервер продолжает работу, фазы пропускаются |
| `stop_graceful` | команда `stop`: сервер и все клиенты (включая монитор) завершаются с кодом 0 |
| `sigint_server` | `SIGINT` серверу: корректный останов всех программ |
| `max_ticks` | завершение по пределу тактов |
| `seeds` | разные seed дают разные результаты |
| `repeatable` | одинаковый seed -> побайтово одинаковая итоговая статистика |
| `wrong_id` | некорректный `--id` отклоняется сервером с пояснением |

Прогон: 17/17. Тесты используют сквозные порты (базовый 48300, переменная `BASE_PORT`), поэтому не конфликтуют с занятыми, и `scripts/cleanup.sh` перед каждой проверкой.

## 14. Выводы

Модель «огонь по движущимся танкам» реализована через TCP клиент-сервер без изменения правил и с сохранением детерминизма. Система состоит из пяти независимых консольных программ, свободно размещаемых на одной или нескольких машинах (адрес и порт в командной строке); асинхронность достигается мультиплексированием `poll`/`select` внутри однопоточных процессов. Сервер централизует состояние и валидацию, благодаря чему инварианты модели не зависят от корректности клиентов; обрыв любого соединения (в том числе `kill -9`) не рушит игру, мониторы и оператор подключаются/отключаются динамически, а завершение по любой причине корректно доводится до всех подключённых программ. Поведение покрыто тестовым набором из 17 проверок (полный сценарий, мониторы, kick/kill с переподключением, останов по `stop`/`SIGINT`, предел тактов, различие и повторяемость seed, отказ в подключении).
