# Домашнее задание №3

Сиротина Дарья Николаевна, БПИ253. Вариант 23 «Огонь по движущимся танкам».

## 1. Постановка задачи

На прямоугольном поле перемещаются танки, а одно или несколько орудий пытаются их поразить. Каждый танк занимает одну клетку и на каждом такте может остаться на месте либо перейти в соседнюю допустимую клетку. Орудие получает сведения о последнем известном положении цели и выбирает координаты выстрела по случайной или прогнозирующей стратегии (не обязательно в позицию танка, пытаясь предугадать его возможное перемещение). Выстрел имеет задержку между наведением и попаданием. После формирования выстрела танк может переместиться, поэтому снаряд поражает указанную клетку, а не идентификатор цели. В одной клетке могут действовать правила прямого попадания, близкого разрыва и промаха.

Требуется разработать консольное приложение, моделирующее огонь по движущимся целям. Каждое орудие и танк, а также координатор поля являются самостоятельными участниками модели - в данном задании это **процессы**, а взаимодействие между ними строится средствами межпроцессного взаимодействия POSIX (семафоры, разделяемая память, каналы FIFO) с обязательной гарантированной очисткой всех IPC-объектов при любом способе завершения, включая `SIGINT` с клавиатуры.

**Входные параметры:**

- размеры поля и препятствия;
- число и начальные позиции танков и орудий;
- стратегии движения;
- дальность наблюдения;
- задержка и точность выстрела;
- радиус поражения (на выбор: от одной клетки до некоторого ущерба в соседних);
- запас снарядов и прочность танков;
- предельное число тактов.

**Отображаемые события.** Программа отображает перемещение танка, наблюдение цели, выбор точки прицеливания, выстрел, фактическое положение цели в момент попадания, промах, повреждение и уничтожение.

**Инварианты:**

- танк не выходит за границы и не проходит через препятствие;
- один выстрел расходует один снаряд;
- попадание определяется по состоянию поля в момент разрыва;
- уничтоженный танк больше не перемещается и становится препятствием;
- значение прочности не становится отрицательным без фиксации уничтожения.

**Завершение.** Моделирование завершается после уничтожения всех танков, исчерпания боеприпасов или достижения ограничения тактов, или по прерыванию пользователем, если задан режим неограниченного по времени выполнения.

## 2. Сценарий

Отображение сущностей модели на процессы и файлы кода:

| Сущность модели | Процесс | Общие файлы |
|---|---|---|
| Поле (координатор) | процесс-родитель в A/B; отдельная программа `coord` / `coord_fifo` в C/D | `field.c`, `coord.c`, `coord_fifo.c` |
| Танк i | дочерний процесс после `fork()` в A/B; программа `ent_tank` / `ent_tank_fifo` в C/D | `proc.c`, `ent_tank.c`, `ent_tank_fifo.c` |
| Орудие j | аналогично танку | `proc.c`, `ent_gun.c`, `ent_gun_fifo.c` |
| Состояние поля, танков, орудий, снарядов | структура `SharedState` в сегменте разделяемой памяти (A/B/C) или локальная структура координатора с рассылкой снимков через FIFO (D) | `state.h`, `shmutil.c`, `msg.c` |
| Координатор всей имитации | цикл тактов в процессе-координаторе | `coord.c` |
| Наблюдатель (журнал) | функции `io_printf`/`log_*` с бинарным семафором-замком вывода | `io.c`, `log.c`, `stats.c` |
| Генератор случайных чисел | `struct Rng` на `rand_r` с состоянием, независимым от глобального; каждый процесс инициализирует свой ГСЧ детерминированно из базового seed | `rng.c` |

Модельное время целочисленное (`long long tick`). Обработка идёт по тактам, внутри такта четыре фазы в фиксированном порядке:

1. `MOVE` - перемещения танков;
2. `OBSERVE` - наблюдения орудий;
3. `FIRE` - выстрелы;
4. `IMPACT` - разрывы снарядов.

Такой порядок обеспечивает инвариант «попадание определяется по состоянию поля в момент разрыва»: разрывы обрабатываются после всех перемещений того же такта. Детали протокола взаимодействия процессов в каждой фазе  в разделах 10–13.

## 3. Установленные правила

### 3.1. Поле и перемещение

- Поле прямоугольное, задаётся w × h, координаты клеток  (x, y), x ∈ [0, w−1], y ∈ [0, h−1].
- Каждая клетка имеет одно из трёх состояний: пусто (`CELL_EMPTY`), препятствие (`CELL_OBSTACLE`), обломки (`CELL_WRECK`).
- Препятствия задаются из конфигурации; обломки появляются при уничтожении танка.
- Шаг танка - на одну клетку по одной из четырёх сторон (N, E, S, W) либо «стоять». Диагоналей нет.
- Танк может шагнуть в клетку, если она в границах поля, не препятствие, не обломки и не занята другим живым танком.
- Танки блокируют друг друга: два танка никогда не окажутся в одной клетке.
- Живой танк не блокирует движение орудия (орудия стоят вне игрового процесса перемещений), но занимает свою клетку.

### 3.2. Стратегии движения танка

| Стратегия | Правило |
|---|---|
| `stay` | Танк всегда остаётся на месте. |
| `random_walk` | На каждом такте равновероятно выбирается одно из 5 действий (4 шага + «стоять»), но только среди допустимых; если все шаги запрещены, танк стоит. |
| `straight` | Танк идёт в текущем направлении, пока не упрётся (в границу, препятствие, обломки или другой танк). После упора выбирает направление (влево/вправо равновероятно). |
| `patrol` | Танк ходит между двумя точками A и B: сначала сокращает \|dx\|, затем \|dy\|. При достижении точки маршрут переключается. Если прямое движение заблокировано - пробует вторую ось. Если и она закрыта - стоит. |

Движение планируется на каждый такт: обработчик фазы MOVE по завершении всегда планирует следующий шаг на t+1, если танк жив.

### 3.3. Наблюдение орудия

- Дальность наблюдения  по манхэттенскому расстоянию: d = |x_gun - x_tank| + |y_gun - y_tank|.
- Орудие на каждом такте (фаза OBSERVE) ищет всех живых танков в радиусе `range` и запоминает ближайшего как текущую цель.
- Для цели хранятся две точки: `last` (последняя виденная) и `prev` (виденная до неё). `prev` нужна для стратегии прогнозирования.
- Если ни одного танка в радиусе нет, цель считается потерянной, `has_target = 0`. Орудие не стреляет, пока не восстановит цель.
- Наблюдение повторяется каждый такт - орудие работает с самой актуальной на текущий момент информацией о цели.

### 3.4. Выбор точки прицеливания

Орудие (фаза FIRE) выбирает точку по одной из трёх стратегий:

| Стратегия | Формула |
|---|---|
| `last` | (last_x, last_y) |
| `predict` | (last_x + (last_x − prev_x), last_y + (last_y − prev_y)) |
| `random` | (last_x ± 2, last_y ± 2)  случайное смещение вокруг последней позиции |

Далее применяется имитация неточности: с вероятностью (100 - accuracy)% к прицелу добавляется случайное смещение (±1, ±1). Точка зажимается в границы поля. Снаряд летит в клетку, а не в идентификатор танка.

### 3.5. Выстрел и снаряд

- Выстрел возможен только если у орудия `ammo > 0` и `has_target = 1`.
- Каждый выстрел списывает один снаряд: `ammo--`.
- Перезарядка: следующая попытка выстрела планируется на `t + reload`, независимо от того, был ли произведён выстрел (таким образом, «пустая» попытка тоже расходует темп перезарядки).
- Каждому снаряду назначается время разрыва `impact_time = t + shot_delay`. Снаряд учитывается в массиве `projectiles` и снимается с учёта после разрыва.

### 3.6. Разрыв снаряда

Для каждого живого танка вычисляется манхэттенское расстояние до клетки разрыва:

| Условие | Класс | Урон |
|---|---|---|
| d == 0 | прямое попадание | `damage_direct` |
| 0 < d ≤ blast_radius | близкий разрыв | `damage_splash` |
| d > blast_radius | промах |  |

Один разрыв может поразить несколько танков одновременно (например, при большом радиусе). Если поражён хотя бы один танк, выстрел засчитывается как попадание, иначе - как промах.

### 3.7. Урон и уничтожение танка

- `hp` уменьшается на величину урона.
- Инвариант «hp не становится отрицательным без фиксации уничтожения»: перед присваиванием проверяется, что `hp - dmg ≤ 0`; в этом случае `hp` принудительно устанавливается в 0, и фиксируется факт уничтожения.
- Уничтоженный танк:
  - перестаёт двигаться (`alive = 0`, следующее перемещение не планируется);
  - становится препятствием: клетка помечается `CELL_WRECK`, другие танки через неё проходить не могут;
  - исключается из всех проверок наблюдения и попадания.

### 3.8. Условия завершения

Моделирование завершается при первом из событий:

1. все танки уничтожены  `REASON_ALL_DESTROYED`;
2. у всех орудий `ammo == 0` и в воздухе нет снарядов  `REASON_NO_AMMO`;
3. `tick ≥ max_ticks` (если `max_ticks > 0`)  `REASON_MAX_TICKS`;
4. поступил `SIGINT` или `SIGTERM` -> `REASON_INTERRUPTED`.

По любому из вариантов программа печатает причину завершения, итоговую статистику и корректно освобождает ресурсы.

### 4.3. Файл конфигурации

Формат - `ключ значение` в строке. Файл перебивает значения по умолчанию, но **уступает** явным аргументам командной строки.

### 4.4. Интерактивный диалог

Запускается флагом `--interactive`. Каждый вопрос допускает пустой ответ, тогда принимается значение по умолчанию (оно показано в `[...]`). Ввод валидируется, при ошибке запрос повторяется с пояснением.

Порядок ввода:

1. Seed - если 0, берётся текущее системное время.
2. Поле: ширина и высота.
3. Препятствия: количество (размещение - автоматическое с проверкой занятости).
4. Танки: количество, прочность (hp), стратегия движения.
5. Орудия: количество, боезапас, дальность наблюдения, перезарядка и задержка в полёте, точность прицела, радиус поражения, урон в клетке попадания, урон в радиусе, стратегия прицеливания.
6. Параметры симуляции: задержка между тактами, предел тактов, флаг печати поля.

По завершении ввода печатается сводка конфигурации - пользователь видит, что именно будет запущено.

## 5. Расшифровка ввода

### 5.1. [ГСЧ]

- Seed (0 = случайный) - начальное состояние генератора. Одинаковый seed -> идентичный прогон (воспроизводимость).

### 5.2. [Поле]

- Ширина - количество клеток по оси X (мин. 2, макс. 200).
- Высота - количество клеток по оси Y (мин. 2, макс. 200).

### 5.3. [Препятствия]

- Сколько препятствий? - сколько статичных клеток закрыть. Диапазон `0..w·h-1`. Координаты выбираются ГСЧ с проверкой на занятость.

### 5.4. [Танки]

- Сколько танков?  0..32.
- Прочность (hp) - начальное здоровье (1..100000). Урон вычитается из него; при hp ≤ 0 танк уничтожается.
- Стратегия движения - одна из четырёх (3.2).
- Начальные позиции выбираются автоматически: клетка должна быть проходимой и не занятой другим танком.

### 5.5. [Орудия]

- Сколько орудий?  0..16.
- Боезапас - сколько всего выстрелов может сделать орудие (0..100000). Каждый выстрел списывает единицу.
- Дальность наблюдения - максимальное манхэттенское расстояние до танка, при котором орудие его видит.
- Перезарядка (тактов) - сколько тактов проходит между двумя попытками выстрела.
- Задержка полёта снаряда (тактов) - сколько тактов снаряд летит до разрыва.
- Точность прицела (0..100) - вероятность, что прицел не будет искажён; при 100 - идеальное наведение, при 0 - всегда смещение ±1.
- Радиус поражения - максимальное манхэттенское расстояние от точки разрыва, в котором танк получает урон. 0 - только клетка попадания.
- Урон в клетке попадания - урон при прямом попадании (d = 0).
- Урон в радиусе - урон при близком разрыве (0 < d ≤ blast_radius).
- Стратегия прицеливания - `random`, `last`, `predict`.

### 5.6. [Параметры симуляции]

- Задержка между тактами, мс - пауза `nanosleep` между тактами (0 - без задержки, для тестов).
- Предел тактов (0 = без предела) - сколько тактов максимум моделировать.
- Печатать состояние поля каждый такт?  по умолчанию [n]; если [y], перед каждым тактом будет напечатано поле (эквивалент флага `--verbose-field`).

### 6.3. Прерывание

- Ctrl+C в терминале посылает `SIGINT`;
- `kill` посылает `SIGTERM`;
- оба обрабатываются одинаково: цикл завершается на ближайшей итерации (не позднее ~1 с - сторожевой таймер ожиданий), печатается статистика, лог закрывается через `fsync` и `close`.

## 7. Реализация пользовательского интерфейса (техническая часть)

Ввод через системный вызов `read(STDIN_FILENO, ...)` по одному байту; такое чтение устойчиво к пайпам и к длинным строкам, идущим через `echo` или перенаправление. Вывод через `write(STDOUT_FILENO, ...)`; форматирование строки выполняется `vsnprintf` в стековый буфер, а сам вывод - системным вызовом (ввод-вывод через дескрипторы).

Так как участников модели несколько и все они печатают, вывод сериализуется бинарным семафором `print`: каждый процесс захватывает его на время печати своей строки, поэтому строки разных процессов не перемешаются. Сообщения снабжаются префиксами `[TANK#i]`, `[GUN#j]`; координатор печатает без префикса. В реализациях C и D дополнительно печатаются сообщения о подключении сущностей («Подключено: k/N»).

Лог - открывается через `open(O_WRONLY | O_CREAT | O_TRUNC)`. Дублирование вывода достигается функцией `io_set_mirror(fd)`: каждый вызов `io_printf` дополнительно пишет ту же строку в лог-дескриптор. При завершении лог синхронизируется через `fsync` и закрывается через `close`.

Задержки - `nanosleep`, что корректно реагирует на сигналы (без `SA_RESTART`): Ctrl+C прерывает паузу, и цикл проверяет флаг.

Обработчики сигналов - устанавливаются через `sigaction` на `SIGINT` и `SIGTERM`. Обработчик только выставляет `volatile sig_atomic_t`. `SA_RESTART` намеренно не устанавливается: заблокированные вызовы (`sem_timedwait`, `read`) прерываются сигналом с `EINTR`, и ожидающий цикл сразу замечает флаг останова - это и есть механизм гарантированной реакции на Ctrl+C.

## 8. Требования к средствам IPC и обзор решения

Задание требует заменить потоки на процессы и построить взаимодействие средствами POSIX с гарантированной очисткой IPC-объектов при любом завершении. По требованиям предусмотрены четыре варианта реализации:

| Реализация | Процессы | Средства IPC |
|---|---|---|
| A | один программный процесс, `fork()` | именованные семафоры POSIX + разделяемая память POSIX |
| B | один программный процесс, `fork()` | неименованные семафоры, размещённые в разделяемой памяти |
| C | независимые, отдельно запускаемые программы | именованные семафоры + разделяемая память |
| D | независимые, отдельно запускаемые программы | именованные семафоры + каналы FIFO (без разделяемой памяти) |

Разработаны **все четыре реализации (A–D)**. Они построены на общем ядре (модель, логика, протокол фаз), что позволило сосредоточиться в каждой реализации именно на средствах синхронизации и обмена.

## 9. Протокол взаимодействия процессов

**Протокол (A/B/C).** Все процессы-участники работают с сегментом разделяемой памяти, защищённым бинарным семафором `mutex`. Каждый такт координатор проводит четыре фазы в фиксированном порядке (инвариант «разрыв  по состоянию поля в момент разрыва» сохранён):

1. `MOVE` - координатор выставляет номер такта, печатает поле (опционально), делает паузу `--delay`, затем поднимает семафор `go` каждого танка; каждый танк под мьютексом выбирает и применяет шаг, затем сообщает о завершении через считающий семафор `done`;
2. `OBSERVE` - то же для орудий (обновление наблюдений);
3. `FIRE` - повторный подъём `go` орудий; орудие вычисляет точку прицеливания только если прошла перезарядка (`tick ≥ next_fire`), выстрел применяется под мьютексом;
4. `IMPACT` - разрывы снарядов с `impact_time ≤ tick` обрабатывает сам координатор.

Координатор в фазах ждёт `done` через `sem_timedwait` (1 с) с проверкой флага останова и живости процессов - это сторожевой таймер: гибель любого участника не блокирует систему навсегда.

**Протокол (D, без разделяемой памяти).** Состояние полностью принадлежит координатору. Для каждой сущности создаётся пара именованных FIFO: `req` (сущность -> координатор) и `rep` (координатор -> сущность), плюс именованный семафор `ready_<роль>_<id>` на каждую сущность. В фазе координатор рассылает контекст фиксированным сообщением `Msg` (снимок поля, танков, состояния орудия, номер такта), поднимает `ready`, ждёт `done`, читает ответ и применяет его к **своему** состоянию; сущность может лишь *предложить* ход - валидация (границы, препятствия, занятость клетки, боезапас, перезарядка) остаётся у координатора. Рукопожатие при подключении устроено так, чтобы избежать взаимной блокировки открытия FIFO: сущность открывает `req` на запись (блокируется до открытия координатором на чтение), сразу отправляет attach-сообщение со своим PID, открывает семафоры и постит семафор `admin`; координатор открывает `req` на чтение, читает attach, `ready`семафоры к этому моменту уже созданы на старте координатора, ждёт `admin`, открывает `rep` на запись и отправляет подтверждение с PID координатора и базовым seed.

**Завершение.** Координатор по условию модели (все танки уничтожены / боезапас исчерпан / предел тактов) или по `SIGINT`/`SIGTERM` переводит состояние в «стоп»: выставляет флаг `stop`, будит всех участников, при необходимости завершает выжившие процессы через `SIGTERM`, после чего на каждом пути выхода выполняет полную очистку: `sem_close`+`sem_unlink` всех именованных семафоров, `munmap`+`shm_unlink` сегмента (A/B/C), закрытие дескрипторов и `unlink` FIFO (D). Дополнительно в проект включён `scripts/cleanup.sh` на случай аварийного `kill -9`.

Во всех реализациях ожидания построены на `sem_timedwait` с секундным таймаутом как сторожевом таймере: участник проверяет флаг `stop`, свой флаг сигнала и живость координатора (`kill(pid, 0)`), поэтому зависание любого процесса не останавливает систему навсегда, а `SIGINT` обрабатывается с задержкой не более ~1 с.

## 11. Реализация A: fork + именованные семафоры + shm

Один исполняемый файл `sim_named`. Процесс-родитель создаёт сегмент разделяемой памяти (`shm_open(O_CREAT|O_EXCL)` + `ftruncate` + `mmap(MAP_SHARED)`), строит начальное состояние, открывает именованные семафоры, затем `fork()`-ом порождает по процессу на каждую сущность. Дочерние процессы наследуют отображённую память и открытые семафоры и работают по протоколу фаз из раздела 9. Дочерний код намеренно минимален: `exit(tank_proc_main(...))` / `exit(gun_proc_main(...))` -  все ресурсы освобождает родитель (`waitpid` + `sem_unlink`/`shm_unlink` при любом исходе). Имена объектов: `/akos3a_shm`, `/akos3a_mutex`, `/akos3a_done`, `/akos3a_print`, `/akos3a_go_<slot>`.

## 12. Реализация B: неименованные семафоры в разделяемой памяти

Координатор инициализирует все семафоры через `sem_init(&hdr.x, 1, init)` до `fork()`; дочерние процессы получают их уже работающими (общая память). Именованных объектов в системе не остаётся вовсе; очистка `sem_destroy` для каждого семафора + `munmap` + `shm_unlink`. За счёт наследования при `fork()` отпадает необходимость открывать семафоры по именам.

## 13. Реализация C: независимые программы + shm

Три исполняемых файла: `coord`, `ent_tank`, `ent_gun`, запускаемые независимо (в любом порядке; сущности могут перезапускаться). `coord` создаёт сегмент `/akos3c_shm` и семейство `/akos3c_*`, публикует свой PID в состоянии и ожидает подключения ровно `tank_count + gun_count` сущностей по семафору `admin`: каждая сущность после открытия всех объектов публикует свой PID в `entity_pids[slot]` под мьютексом и постит `admin`. Публикация PID нужна для корректного завершения: координатор знает, кому посылать `SIGTERM`, а сущности - кому «подмигивать» через `kill(pid, 0)`. Сущность при выходе только закрывает дескрипторы (`sem_close`, `munmap`) и **никогда** не удаляет объекты - unlink выполняет исключительно координатор. Порядок запуска не важен: если сущность стартовала раньше координатора, `entity_attach` ждёт появления сегмента и семафоров (`shm_attach_wait`, `sem_open_wait`, повтор каждые 100 мс, общий лимит 10 с), поэтому одновременный запуск всех процессов не приводит к ошибкам «No such file or directory».

## 14. Реализация D: независимые программы + FIFO-каналы

Файлы `coord_fifo`, `ent_tank_fifo`, `ent_gun_fifo`. Разделяемой памяти нет: состояние - локальная структура координатора, сущности обмениваются с ним сообщениями фиксированного размера `Msg` (фаза, идентификатор, PID, номер такта, seed, снимок поля и танков, состояние орудия, координаты ответа) через пары FIFO `/tmp/akos3d_{req,rep}_{tank,gun}_{id}`. Синхронизация - именованные семафоры `/akos3d_{print,done,admin,ready_<роль>_<id>}`. Ключевые решения:

- **Порядок рукопожатия исключает deadlock открытия FIFO**: сущность сначала открывает `req` на запись (с повтором попыток в неблокирующем режиме до 10 с, пока координатор не откроет читающий конец) и сразу отправляет attach-сообщение, семафоры открывает с ожиданием их появления (`sem_open_wait`), до поста `admin`, а `rep` открывает после; координатор читает attach до ожидания `admin`, а `ready`-семафоры создаются на старте координатора, до подключения любой сущности (устранена гонка «сущность открывает ready раньше, чем он создан»). Как и в C, порядок и момент запуска процессов произвольны;
- **Координатор - единственный владелец состояния**: ответы сущностей проходят валидацию (`field_is_passable`, занятость клетки, перезарядка `next_fire`, боезапас), поэтому недопустимый ход от сущности не портит модель;
- очистка: координатор рассылает сообщение `PH_STOP`, будит семафоры `ready`, даёт сущностям 1 с на корректный выход, добивает выживших `SIGTERM`, затем закрывает дескрипторы, удаляет семафоры и unlink-ает все FIFO.

## 15. Сборка, запуск и завершение

Сборка: `make` (все 8 исполняемых файлов; объектные файлы  в `build/`; флаги `-std=c11 -Wall -Wextra -O2`, без предупреждений). Дополнительные цели: `make run` (запуск реализации A с `$(ARGS)`), `make doc` (Doxygen по `Doxyfile`, каталог `include/`), `make test` (прогон тестов), `make clean-all` (сборка + документация + логи тестов). Запуск:

```bash
# A / B (одна программа)
./sim_named    [параметры] [--log файл]
./sim_unnamed  [параметры] [--log файл]

# C (координатор + сущности в отдельных терминалах/фоне)
./coord [параметры] [--log файл] &
./ent_tank --id 1 & ./ent_tank --id 2 & ./ent_tank --id 3 &
./ent_gun --id 1 &  ./ent_gun --id 2 &

# D (аналогично)
./coord_fifo [параметры] [--log файл] &
./ent_tank_fifo --id 1 & ... ./ent_gun_fifo --id 2 &
```

Набор сущностей и их идентификаторы в C/D определяются параметрами координатора: `ent_tank --id N` допустим при `N ≤ --tanks`, `ent_gun --id N` при `N ≤ --guns`.

**Варианты завершения** (все проверены тестами): штатное по условию модели; `Ctrl+C` (`SIGINT`) в любой реализации корректный останов с печатью итоговой статистики и причиной «прервано пользователем», код выхода 0; `SIGTERM` сущностям от координатора; убийство координатора - сущности замечают это сторожевым таймером в течение ~1 с и завершаются сами. После любого завершения в системе не остаётся ни семафоров, ни сегментов, ни FIFO (проверяется тестом; при `kill -9` - `scripts/cleanup.sh`).

## 17. Тестовые наборы

`tests/run_all.sh` (запускается через `make test`) выводит в консоль статус каждой проверки (`[имя] OK/FAIL`) и итоговую сводку «пройдено N, провалено M»; подробные логи сохраняются в `tests/out/*.log`. Всего 40 проверок, **каждая реализация прогоняется через единый набор** (имя теста начинается с `a_`, `b_`, `c_` или `d_`):

**Единый набор для каждой реализации:** справка `--help`; выстрел происходит (в логе есть `ВЫСТРЕЛ`); завершение по пределу тактов (`--max-ticks 3`); разные seed дают разные результаты (прогоны с seed 1 и 42, логи сравниваются); полный сценарий из раздела 16 завершается штатно с ожидаемым исходом «все танки уничтожены» и полной итоговой статистикой (блоки «Орудия:», «Танки:», «Причина завершения»); корректная обработка `SIGINT`  останов по сигналу, строка «прервано пользователем», код возврата 0. Для C и D каждый прогон запускает координатора в фоне и подключает 3 танка и 2 орудия; координатор обязан завершиться сам в течение 90 с, иначе тест считается проваленным. Дополнительно для C и D есть тесты `c_race`/`d_race`: координатор и все сущности стартуют **одновременно** (без паузы), ожидается подключение 5/5, сущности обязаны сами дождаться появления объектов координатора.

**Общие проверки:** эквивалентность - итоговый блок статистики (от «Орудия:» до «Причина завершения») совпадает во всех четырёх логах полного сценария; контроль утечек IPC - отсутствие `/dev/shm/sem.akos3*`, `/dev/shm/akos3*`, `/tmp/akos3d_*` после всех прогонов. Перед каждым тестом набор автоматически очищает IPC-объекты от предыдущих прогонов, поэтому последовательные запуски стабильны.
